# Stage 3 authentication and recovery

Use synthetic credentials only. The SQLite development database remains plaintext. Passwords and recovery codes have separate one-way verifiers, but a party with write access to the database can replace verifiers, modify account assignments or manipulate audit records. Stage 3 provides application controls for cooperative development use.

## First launch and sign-in

Initialize a new development database explicitly or point the application at an existing Stage 1–2 database using the README commands. If neither database nor path is configured, the application shows a setup instruction with the billing shell locked. An established database or installation marker that becomes missing or inconsistent stops startup. Stage 3 uses the original migration and preserves prior records.

Setup is available when the installation is marked `NotConfigured` and has no Super Admin assignment. It accepts a 3–40 character ASCII username using letters, digits, dots, underscores and hyphens, with case-insensitive normalization consistent with SQLite. The passphrase must contain at least 15 Unicode scalar values, match its confirmation and fit within 512 UTF-16 code units. Malformed UTF-16 and all-whitespace input are rejected. No predefined credentials or character-class rules are used.

An SQLite writer transaction serializes setup before reading eligibility. The new user, singleton assignment, ten salted code verifiers, setup completion and audit event commit together. The existing unique username and singleton constraints provide an independent concurrency check. Failure before commit leaves setup unconfigured. After commit, the application shows the plaintext codes once. If the app exits or display fails between commit and presentation, the installed administrator can sign in with the chosen password and regenerate the codes after entering that password again.

Sign in using the GTS username and password. Windows account sign-in grants no GTS session. The authenticated shell offers 19 planned destinations and the relevant Stage 3 account actions. Sign out clears the in-process identity and returns to login without closing the app. Protected operations validate the current active user and account version against SQLite each time. Password recovery increments that version, invalidating existing sessions on their next check. Stage 3 does not coordinate machine-wide graphical sessions.

## Password and recovery policy

The infrastructure adapter uses Bouncy Castle Cryptography 2.7.0, a maintained MIT-licensed package with .NET 6 and .NET Standard 2.0 assets. .NET 10 compatibility was verified through package restore, build and the tests. It supplies Argon2id v1.3 with 64 MiB, three iterations, parallelism one, a random 16-byte salt and a 32-byte result. The stored representation records the profile. Verification accepts bounded, explicitly supported profiles and compares digest bytes in constant time. A compatibility profile and an upgrade check allow future revisions to change parameters. Stage 3 does not rewrite a stored verifier during login. [Package and license](https://www.nuget.org/packages/BouncyCastle.Cryptography/2.7.0)

Five failures in 30 seconds block further attempts in the same operation category. Login, recovery and regeneration reauthentication each have separate installation-wide buckets derived from committed audit history. Restarting the process does not clear them. Throttled requests do not extend the window. During a burst, legitimate users in the same installation can be affected. Clock manipulation and direct database access are outside this control's trust boundary. Login responses use the same message for unknown, disabled and wrong-password accounts.

Each code has 160 random bits displayed as eight groups of four symbols, excluding ambiguous characters. SQLite stores an independently salted SHA-256 verifier for each randomly generated code. Passwords use Argon2id because human-chosen phrases have a different guessing risk. The code list is available only following the committed setup or regeneration transaction. Continue or closing the window discards the display. Managed strings may remain in process memory until collected.

**Print** opens the Windows print dialog through the Printing project. Choose a trusted printer and collect the output. **Save** opens a destination picker and creates a labeled sensitive plaintext text file at the chosen path. The save operation refuses existing files and paths under the repository, database folder or application folder. Choose a private location. Exported files, printer queues and physical output have their own access and retention risks.

At login, choose **Recover Super Admin password**, enter one unused code and confirm a new passphrase. Code consumption, the password change and its audit records commit together. Recovery always targets the assigned Super Admin. Once used, a code is unavailable. From the authenticated shell, **Regenerate recovery codes** requires the current Super Admin password. It revokes the remaining old codes and commits ten new verifiers together. Losing both the password and every usable code leaves no built-in recovery path. Codes do not decrypt or restore databases.

Audit records contain timestamps, installation ID, known actor ID, action and outcome. Neither these records nor ordinary diagnostics contain submitted credentials or plaintext codes. EF's sensitive data logging remains disabled. Password fields use masked controls, clear on submission and are not bound to retained view-model properties.
