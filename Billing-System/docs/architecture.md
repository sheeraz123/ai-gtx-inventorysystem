# Stages 1–2 architecture and boundaries

Five application projects: Presentation.Wpf -> Application; Application -> Domain; Infrastructure -> Application (Domain available transitively); Printing -> Application. Presentation references Infrastructure and Printing at the composition root. One Windows-targeted xUnit project verifies the foundation and persistence. A reference-direction test guards this boundary.

CommunityToolkit.Mvvm supplies ObservableObject and RelayCommand. ShellViewModel contains only navigation/display state, no SQL or persistence calls. All 19 navigation destinations are explicit planned placeholders. The WPF process composes a Microsoft.Extensions.Hosting container with default external configuration providers disabled and local appsettings.json explicitly loaded. No hosted background workers exist.

Application defines IDatabaseLocation, IDevelopmentDatabase, ICompanyReader, IUnitOfWork and IDataTransaction. Infrastructure implements them. EF is not exposed to view models. BillingDbContext implements async persistence and transactions and adds optimistic Version checks to record updates. Callers must use SaveChangesAsync; no business use cases are exposed yet.

DevelopmentDatabase takes one explicit absolute configured path; it never derives an operational path from a Windows user's profile. A shell-only launch is permitted without any path. Initialization is an explicit developer command, not a first-run Super Admin workflow. A ready sidecar plus matching database Installation ID is required for subsequent opening. An absent expected file, marker mismatch or incomplete state stops startup. No EnsureCreated fallback exists.

Migration 20261116000100_InitialDevelopmentSchema uses a frozen SQL resource plus invariant triggers. Target model and snapshot are generated by EF Core design-time services, which are test-only dependencies. MigrationArtifacts tests reproduce/compare the snapshot. The explicit --export-schema developer command generates base DDL from the EF model; it does not generate trigger definitions and must not be used to initialize operational data. Automatic migration on normal launch and destructive Down migration are disabled.

Logging deliberately records event identifiers rather than messages/exceptions that might carry sensitive values. Unhandled UI errors stop the process; the foundation does not attempt to keep operating after an unknown persistence error. Shutdown stops/disposes DI hosting with a bounded cancellation period.

Not implemented: machine-wide operational session locks, application login, authorization, password hashing, recovery codes, encryption/key protection, shared Windows provisioning, Company CRUD, numbering allocation services, backup jobs, printing workflows. Tables for these future capabilities do not make the capabilities operational.

AI-Harness remains independent and unexecuted. This stage does not satisfy final production encryption or hostile-user isolation requirements.
